## 1. Basic Categories of DoS/DDoS Attack Vectors

*(Source: EC-Council CEH v13)*

All DoS/DDoS attacks fall into three broad categories based on the resource they exhaust:

| Category | Target Resource | Unit of Measurement | EC-Council Examples |
| :--- | :--- | :--- | :--- |
| **Volumetric** | Network Bandwidth | Bits per second (bps) | UDP Flood, ICMP Flood, PoD, Smurf, Pulse Wave, NTP Amplification |
| **Protocol** | State Tables (firewalls, LBs, servers) | Packets per second (pps) / Connections per second (cps) | SYN Flood, Fragmentation, ACK Flood, TCP SACK Panic, Spoofed Session |
| **Application Layer** | CPU / Memory / App Resources | Requests per second (rps) | HTTP GET/POST Flood, Slowloris, UDP App Layer Flood, DDoS Extortion |

## 2. Volumetric Attacks

*(Source: EC-Council CEH v13)*

### 2.1 UDP Flood Attack
An attacker sends **spoofed UDP packets at a very high packet rate** to random ports on a target server using a large source IP range. The server checks for non-existent applications at those ports, finds none, and generates **ICMP "Destination Unreachable"** replies. This exhausts network resources and available bandwidth until the network goes offline.

### 2.2 ICMP Flood Attack (Ping Flood)
Attackers send **large volumes of ICMP Echo Request packets** directly to the victim or through reflection networks. The victim's system responds to each request, and the combined traffic saturates the bandwidth of the victim's network connection. The victim stops responding to legitimate TCP/IP requests.

**ICMP Flood Countermeasure (EC-Council):** Set an ICMP flood threshold. When exceeded (default: **1000 packets/second**), the router rejects further ICMP echo requests from all addresses in the same security zone for the remainder of the current second plus the next second.

### 2.3 Ping of Death (PoD) Attack
An attacker attempts to **crash, destabilise, or freeze** the target system by sending **malformed or oversized packets** using a simple `ping` command.

* **RFC 791 IP limit:** 65,535 bytes maximum packet size
* **Attack:** Attacker sends a packet of 65,538 bytes (or larger via malicious fragments)
* **Result:** The reassembly process on the receiving system causes it to crash
* **Stealth factor:** The attacker's identity can be easily spoofed; attacker only needs the target IP address

### 2.4 Smurf Attack
The attacker **spoofs the source IP with the victim's IP address** and sends a large number of **ICMP ECHO Request packets to an IP broadcast network**. All hosts on the broadcast network respond to the ICMP ECHO requests, sending replies to the victim (because the source IP was spoofed). The victim is crushed by the volume of simultaneous responses.

> **💡 CEH Beginner Tip:** Smurf = ICMP + Broadcast + IP Spoofing. The broadcast network acts as an unwitting amplifier. A Fraggle attack is the same concept but uses **UDP traffic** instead of ICMP.

### 2.5 Pulse Wave DDoS Attack *(EC-Council — CEH v13 New)*
A newer attack pattern where the attack is **periodic rather than continuous**. Attackers send highly repetitive bursts (pulses) of packets to the target **every 10 minutes**, with the session lasting approximately an hour or several days. A single pulse of **300 Gbps or more** is sufficient to crowd a network pipe. Recovery is very difficult and occasionally impossible.

### 2.6 Zero-Day DDoS Attack
DDoS attacks targeting **vulnerabilities for which no patches or effective defensive mechanisms exist**. Until the victim identifies the attack strategy and deploys a patch, the attacker actively blocks all victim resources and potentially steals data. There is **no versatile approach** to protect networks from zero-day DDoS attacks.

### 2.7 NTP Amplification Attack
The Network Time Protocol (NTP) synchronizes time across networks. In this attack:
1. Attacker uses a botnet to send **large UDP packets through a spoofed IP** (victim's IP) to NTP servers
2. Attack is initiated through NTP servers with the **monlist command enabled** — which returns a list of the last **600 IP addresses** that connected to the NTP server
3. The NTP server sends the large response to the spoofed IP (victim)
4. Victim is flooded with massive NTP responses from many NTP servers simultaneously

**Command to test for NTP monlist vulnerability:**
```bash
nmap -sU -pU:123 -Pn -n --script=ntp-monlist <target>
```

**NTP Amplification Countermeasures (EC-Council):**
* Secure and harden NTP server configurations to prevent monlist exploitation
* Limit flow control in the NTP server
* Frequently monitor network for abnormal behavior
* Implement zero-trust network
* Use firewalls to filter NTP server requests

> **💡 Supplementary:** NTP amplification has an amplification factor of **~556x** — one of the highest of any protocol. Memcached amplification exceeds **51,000x**. DNS amplification is approximately **50x**.

## 3. Protocol Attacks

*(Source: EC-Council CEH v13)*

### 3.1 SYN Flood Attack
Exploits the **TCP 3-Way Handshake**.

**Normal 3-Way Handshake:**
1. Client → Server: `SYN` ("I want to connect")
2. Server → Client: `SYN-ACK` ("Okay, I've reserved a slot, confirm")
3. Client → Server: `ACK` ("Confirmed, let's talk")

**The Attack:**
* Attacker sends large numbers of SYN packets with **fake source IP addresses**
* Server responds with SYN-ACKs and keeps connection slots open ("listen queue") for at least **75 seconds**
* The fake ACK never arrives; the queue fills up
* When full, the system cannot open new connections until entries timeout

**Related Attacks:**
* **SYN-ACK Flood:** Attacker exploits the second stage by flooding the target with SYN-ACK packets directly
* **ACK and PUSH ACK Flood:** Attacker sends large amounts of spoofed ACK/PUSH ACK packets, making the target non-functional

**SYN Flood Countermeasures (EC-Council):**
* **SYN Cookies:** Cryptographic technique — server does not allocate memory until the final ACK is received
* **SynAttackProtect** (Windows)
* Decrease timeout period for "SYN RECEIVED" state in the queue
* Decrease the number of packet retransmissions or turn off packet retransmissions

### 3.2 Fragmentation Attack
When large files are sent over the Internet, they are broken into fragments, each with an offset value indicating where it belongs in the reassembly sequence. In this attack, the attacker sends **large numbers of fragmented (1500+ byte) packets** at a small packet rate:
* Because the protocol allows fragmentation, packets often pass **uninspected through routers, firewalls, and IDS/IPS**
* The reassembly and inspection of large fragmented packets consume excessive resources
* The **content is randomized** by the attacker, making reassembly consume even more resources
* Result: system crash or significant performance degradation

**Teardrop Attack (Supplementary):** A specific fragmentation attack where packets are sent with **overlapping offset values**, causing the reassembly process to fail with fatal errors (BSOD on Windows).

### 3.3 Spoofed Session Flood Attack
Attackers create fake/spoofed TCP sessions using multiple SYN, ACK, and RST/FIN packets to **bypass firewalls** and exhaust network resources:

| Variant | Technique |
| :--- | :--- |
| **Multiple SYN-ACK Spoofed** | Fake session with multiple SYN + multiple ACK packets + one or more RST/FIN packets |
| **Multiple ACK Spoofed** | Fake session skipping SYN packets entirely, using only ACK + RST/FIN. Since firewalls mostly filter by SYN packets, DDoS detection rate is very low. |

### 3.4 ACK Flood Attack
Attackers send massive volumes of **spoofed ACK packets** to the target. The target must process each ACK to determine if it corresponds to a valid open connection, consuming significant CPU resources even when no match is found.

### 3.5 TCP State Exhaustion Attack
Targets the **connection state tables** maintained by firewalls, load balancers, and application servers. By opening and manipulating many connections, the attacker fills the state table. Once full, **no new connections can be allowed** regardless of the volume of traffic.

### 3.6 TCP SACK Panic Attack *(EC-Council — CEH v13)*
A remote attack vector targeting **Linux systems** specifically:

* **TCP SACK (Selective Acknowledgment):** Linux informs the sender about packets successfully received so the sender only retransmits missing ones. Linux uses a **linked-list socket buffer (SKB)** to store data — max capacity of **17 segments**
* **The Attack:** Attacker sends specially designed SACK packets with the **MSS (Maximum Segment Size) set to the lowest value (48 bytes)**. The low MSS increases the number of TCP segments to retransmit, causing the socket buffer to exceed 17 segments, triggering **integer overflow → kernel panic → DoS**
* **Scope:** Also works against containers and virtual machines

**TCP SACK Panic Countermeasures:**
* Implement vulnerability patching
* Implement a firewall rule to block requesting packets with the lowest MSS

## 4. Application Layer Attacks (Layer 7)

*(Source: EC-Council CEH v13)*

> Application-layer attacks occur **after a connection is established**. The traffic entering the target appears legitimate, making these attacks very difficult to detect. However, once identified, they can be traced to the source more easily than volumetric DDoS attacks.

### 4.1 HTTP GET/POST Attack
**HTTP GET Attack:** Attacker uses time-delayed HTTP headers to hold on to HTTP connections and exhaust web-server resources. The attacker never sends the full request. The server retains the connection waiting. Network parameters appear healthy while the service remains unavailable.

**HTTP POST Attack:** Attacker sends HTTP requests with **complete headers but an incomplete message body**. The server waits for the rest of the body, blocking the connection. Less bandwidth than other attack types is needed to bring down the targeted site.

**Variants of HTTP flood attacks (EC-Council):**
* **Single-Session HTTP Flood:** Exploits HTTP 1.1 vulnerabilities to bombard target with multiple requests in a single HTTP session
* **Single-Request HTTP Flood:** Multiple HTTP requests concealed within a single HTTP packet — allows attacker anonymity
* **Recursive HTTP GET Flood:** Attacker mimics a legitimate user browsing through pages/images while covertly flooding the target
* **Random Recursive GET Flood:** Tweaked version targeting forums/blogs — uses random page numbers from a valid range to appear as a legitimate user

### 4.2 Slowloris Attack
*(Source: EC-Council CEH v13)*

Slowloris is a DDoS tool that uses **perfectly legitimate HTTP traffic** to take down a target web server. The attacker sends **partial HTTP requests** — the target server opens multiple connections and waits for them to complete. These requests remain incomplete, causing the server's **maximum concurrent connection pool** to fill up and denying additional connections.

> **💡 Supplementary:** Slowloris is specifically devastating against Apache web servers. It is harmless against servers like Nginx or HAProxy that use asynchronous connection handling (non-blocking I/O). The fix: place a reverse proxy or load balancer in front of the Apache server.

### 4.3 UDP Application Layer Flood Attack
Though UDP floods are known as volumetric attacks, some **application-layer protocols that rely on UDP** can be exploited for flooding:

| UDP-Based Protocol | Notes |
| :--- | :--- |
| CHARGEN (Character Generator Protocol) | Generates and sends arbitrary character streams |
| SNMPv2 | Network management — responds with large datasets |
| QOTD (Quote of the Day) | |
| RPC (Remote Procedure Call) | |
| SSDP (Simple Service Discovery Protocol) | Used in UPnP — common amplification vector |
| CLDAP (Connectionless LDAP) | Amplification factor ~56x |
| TFTP | |
| NetBIOS | |
| NTP | *(See Section 2.7)* |
| Quake Network Protocol | |
| Steam Protocol | |
| VoIP | |

### 4.4 DDoS Extortion / Ransom DDoS (RDDoS) Attack
*(Source: EC-Council CEH v13)*

Attackers threaten target organizations with a DDoS attack and demand **ransom payment**:
1. Attacker sends a ransom note OR initiates a **sample DDoS attack** on specific resources to prove capability
2. Email with ransom/extortion note delivered — includes payment option, deadline, digital currency instructions
3. May include threats about exposed vulnerabilities or data
4. Attackers often **fake high-capacity DDoS capability** to extort payment

**RDDoS Countermeasures (EC-Council):**
* Implement effective DDoS defense tools
* Immediately report to law enforcement agencies and security teams
* Frequently evaluate assets for risk tolerance
* Implement mitigation strategies such as **BGP/DNS swing** and **always-on protection service**

## 5. Other Notable Attack Techniques

*(Source: EC-Council CEH v13)*

### 5.1 Peer-to-Peer (P2P) Attack
Exploits bugs in **peer-to-peer servers** to initiate a DDoS attack. Attackers exploit flaws in networks using the **Direct Connect (DC++) protocol** for file sharing between instant-messaging clients.

* **Does not use botnets** — no need to communicate with the clients being subverted
* Attacker instructs clients of large P2P file-sharing hubs to **disconnect from their P2P network** and instead connect to the victim's website
* Thousands of computers aggressively attempt to connect to the target website

**P2P Attack Mitigation:** Specify ports for P2P communication (e.g., disallow port 80 for P2P traffic).

### 5.2 Permanent Denial-of-Service (PDoS) Attack — Phlashing
*(Source: EC-Council CEH v13)*

Also known as **phlashing** — purely targets hardware and causes **irreversible damage**.

* Exploits security flaws to allow remote administration on management interfaces of printers, routers, and networking devices
* **"Bricking" method:** Attacker sends fraudulent hardware update emails/links. Victim installs corrupted/malicious firmware. Attacker gains complete control
* Quicker and more destructive than conventional DoS attacks
* Works with **limited resources** (unlike DDoS which needs many zombies)

### 5.3 Distributed Reflection DoS (DRDoS) Attack
*(Source: EC-Council CEH v13)*

A "spoofed" attack using **multiple intermediary and secondary machines**:

1. Attacker commands **zombie agents** to send TCP SYN packets with the **primary target's IP as the source** to non-compromised **reflector machines**
2. Reflectors believe the victim requested a connection and send **SYN-ACK packets** back to the victim
3. Victim discards the SYN-ACKs (it never sent SYN packets)
4. Reflectors wait for ACK, assume packets were lost, resend SYN-ACKs — until timeout
5. Victim is flooded by combined bandwidth of all reflector machines

> Very difficult or impossible to trace the attacker — the **secondary victims (reflectors) appear** to be attacking the primary target.

**DRDoS Countermeasures (EC-Council):**
* Turn off the **CHARGEN** service
* Download the latest updates and patches for servers

## 6. Multi-Vector and Advanced Attacks

*(Source: EC-Council CEH v13, supplemented)*

### 6.1 Multi-Vector Attack *(EC-Council)*
Attacker uses **combinations of volumetric, protocol, and application layer attacks** simultaneously or sequentially:
* Quickly changes from SYN packets to Layer 7 HTTP floods
* Confuses and divides the IT department's mitigation resources
* Exhausts human responders and automated defenses simultaneously

### 6.2 Supplementary: Memcached Amplification
Memcached is an in-memory caching system used to speed up websites. When left exposed on UDP port 11211:
* Attacker places large payload data in an unprotected Memcached server
* Sends spoofed small request (~15 bytes) to retrieve the data to the victim's IP
* Server sends the massive response to the victim
* **Amplification factor: ~51,000x** — the highest of any known protocol

The **2018 GitHub DDoS attack** peaked at **1.35 Tbps** using Memcached amplification, breaking all previous records at the time.
