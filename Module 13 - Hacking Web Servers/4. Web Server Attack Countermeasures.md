## 1. Place Web Servers in a Secure Segment (DMZ)

An ideal web hosting network should be designed with three segments:
1. **Internet segment**
2. **Secure server security segment (DMZ)**
3. **Internal network**

Placing web servers in the **DMZ** isolates them from the public network and the internal web-hosting network. This adds security barriers allowing administrators to apply strict firewall and access control rules for the internal network as well as for internet traffic toward the DMZ, preventing malicious insiders and outside attackers.

## 2. Patch Management & Updates

### Patches and Hotfixes
* **Patch:** A publicly released update designed to fix problems, security vulnerabilities, or bugs.
* **Hotfix:** A package addressing a critical defect in a live environment containing a fix for a single issue. Occasionally delivered as a combined set called a **service pack**.

### The Automated Patch Management Process
1. **Detect:** Use tools to detect missing security patches.
2. **Assess:** Assess the issues and severity to influence the decision.
3. **Acquire:** Download the patch for testing.
4. **Test:** Install the patch on a test machine to verify consequences.
5. **Deploy:** Deploy the patch to computers ensuring applications are unaffected.
6. **Maintain:** Subscribe to vulnerability notifications.

### Patch Management Best Practices
* Test service packs/hotfixes in a representative **non-production environment** prior to deployment.
* Keep a **back-out plan** to return to the original state if deployment fails.
* Ensure server outages are scheduled and backup tapes are ready.
* Conduct extensive **risk assessments** to determine the most vulnerable network segments.
* Make a detailed inventory of endpoints, services, and dependencies.
* **Tools:** `GFI LanGuard` ([https://www.gfi.com](https://www.gfi.com)), `Symantec Client Management Suite`, `Solarwinds Patch Manager`, `Kaseya Patch Management`, `Software Vulnerability Manager`, `Ivanti Patch for Endpoint Manager`.

## 3. Countermeasures: Protocols & Accounts

### Securing Protocols
* Block all unnecessary ports and **ICMP traffic**.
* Harden the **TCP/IP stack**.
* If insecure protocols (Telnet, SMTP, FTP) are used, secure them with **IPsec policies**.
* Use **TLS/SSL** for communication and **FTPS** for file transfers.
* Redirect all HTTP traffic to **HTTPS** and use **HSTS headers** to prevent downgrade attacks.
* Implement **rate-limiting** to mitigate DDoS attacks targeting the SSL/TLS handshake.
* Isolate LDAP servers from the local subnet.

### Securing User Accounts
* Remove unused modules, application extensions, and default user accounts.
* Follow the **principle of least privilege** for database applications (SQL poisoning defense) and processes.
* Use secure web permissions, NTFS permissions, and **.NET Framework URL authorization**.
* Limit administrator/root-level access and maintain encrypted logs of user activities.
* Implement strong password policies (expiry, locking), **2FA/MFA**, and **CAPTCHA** for bots.
* Use strong one-way hashing algorithms: **bcrypt, scrypt, or Argon2**.
* Use **VPNs** (like OpenVPN) for multi-server platforms.

## 4. Countermeasures: Files & Directories

* Eliminate unnecessary `.jar` files and sensitive configuration info in byte code.
* **Disable directory listings.**
* Avoid mapping virtual directories between two different servers.
* Eliminate archive, backup, text, and header/include files.
* Create a **resource map** to disable serving certain file types.
* Store web apps/files in a **partition separate** from the OS and logs.
* Run the web server in a **sandbox directory**.
* Avoid referencing non-web file types in URLs.
* Use **WAF** to protect against SQL injection and **SFTP** instead of FTP.
* Secure config files (`.htaccess`, `web.config`) from web access.

## 5. Defending Specific Web Server Attacks

### Defending against HTTP Response-Splitting & Web Cache Poisoning
* Remove **Carriage Returns (CR `%0d` / `\r`)** and **Linefeeds (LF `%0a` / `\n`)** before inserting data into an HTTP response header.
* Use **UDP source port randomization** to defend against blind response forgery.
* Limit simultaneous recursive queries and increase **TTLs** of legitimate records.
* Restrict the web application’s access to unique IPs.

### Defending against DNS Hijacking
* Encourage the registrar (ICANN accredited) to set **REGISTRAR-LOCK** on the domain name.
* Change default router passwords and avoid untrusted audio/video codecs.
* Restrict **zone transfers** and use script blockers in the browser.
* Use **DNSSEC (Domain Name System Security Extensions)** to add an extra layer of protection.
* Configure a **master–slave DNS**: Keep the master offline (no internet access) and maintain two slave servers.
* Filter rogue resolvers via firewall.
* Enable **DNS over HTTPS (DoH)** or **DNS over TLS (DoT)** to encrypt queries.
* Implement **geolocation verification** for DNS management interfaces.

### Defending against General Web Server Attacks (Ports, Certs, Config)
* Use a "deny this IP address" rule or a **"routed blackhole"** command to drop spoofed IP attacks.
* Use direct validation of **Server Certificates**, ensuring the public key is valid to the trusted root.
* **Machine.config (.NET):** Map protected resources to `HttpForbiddenHandler`. Disable tracing (`<trace enable="false"/>`) and debugging. Do not revert ASP.NET errors to the client.
* **Code Access Security:** Apply restricted ACLs, secure the SAM, restrict `metabase` file access, remove unused **ISAPI filters/mappings**.

## 6. Detecting Web Server Hacking Attempts

### Website Change Detection System (WDS)
When an attacker installs a backdoor (script), the file size increases. A **Website Change Detection System (WDS)** periodically compares the **hash values** of all executable files (HTML, JS, PHP, ASP, Perl, Python) with their respective master hash values.
* If it detects any change to the codebase, it sends an email alert.
* **Tool Example:** `DirectoryMonitor` (an automated tool that scans web folders for changes and alerts the user).
