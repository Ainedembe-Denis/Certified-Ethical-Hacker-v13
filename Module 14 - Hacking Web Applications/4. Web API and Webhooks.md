## 1. Web API Concepts

A **Web API** is an application programming interface that provides online web services to client-side applications for retrieving and updating data from multiple online sources. Web APIs:
* Make resources accessible on the Internet via the **HTTP protocol**.
* Consist of tools, functions, and protocols to develop software without complexity.
* Centralize business logic updates — reducing complexity of updating each individual client implementation.

**Example benefit:** A traditional web application supported by multiple mobile platforms with no centralized API requires updating business logic for each implementation whenever a change is made. A centralized Web API resolves this.

---

## 2. Types of Web Service APIs

### 1. SOAP API
A web-based communication protocol enabling interactions between applications on different platforms (Windows, macOS, Linux) via **XML and HTTP**.
* Generates, recovers, modifies, and erases different logs such as profiles, credentials, and business leads.

### 2. REST API
**Representational State Transfer (REST)** — an architectural style (not a specification, tool, or framework) that serves as a communication medium between systems on the web.
* Requesting machines receive prompt access to web resource representations.
* Uses stateless protocols and qualitative operations.

### 3. RESTful API
A RESTful service designed using REST principles and HTTP communication protocols.
* Uses HTTP methods: **PUT, POST, GET, DELETE**.
* Makes applications independent, improving performance, visibility, scalability, reliability, and portability.

**RESTful API Characteristics:**

| Property | Description |
| :--- | :--- |
| **Stateless** | Client stores the session state; server is restricted from saving data during request processing. |
| **Cacheable** | Client saves responses in cache to enhance API performance. |
| **Client-Server** | Both sides are independent — server handles backend, client is the front end. |
| **Uniform Interface** | Resources independently identified via a single URL using PUT/POST/GET/DELETE methods. |
| **Layered System** | Multi-layer architecture allows intermediary servers (cache) to achieve scalability — client never directly notifies the main server. |
| **Code on Demand** | Optional — server provides temporary executable code to the client to customize functionality. |

### 4. XML-RPC
**Extensible Markup Language - Remote Procedure Call** — uses a specific XML format to transfer data. Simpler than SOAP and uses less bandwidth.

### 5. JSON-RPC
**JavaScript Object Notation - Remote Procedure Call** — same as XML-RPC but uses **JSON format** instead of XML to transfer data.

## 3. Webhooks

**Webhooks** are user-defined HTTP callback or push APIs raised based on triggered events (e.g., comment received on a post, pushing code to the registry).

* Allows an application to update other applications with the latest information — **real-time** data push.
* Sometimes called **"Reverse APIs"** — the developer creates an API to use a webhook.
* Used to send text messages and notifications to mobile numbers or email addresses.

### How Webhooks Operate:
1. Webhooks are enrolled along with domain registration via the user interface or API.
2. A generated path contains code that automatically executes on a new event occurrence.
3. Systems trace the path to generate notifications.
4. When system-2 gets a notification from the selected path, it becomes aware of new events and can respond.
5. The path is accessed via an **HTTP POST request**.
6. Informs the user of where the message was triggered, including date, time, and event details.

**Visibility:** Webhooks can be **private** or **public**.

### Webhooks vs. APIs
| Feature | Webhooks | APIs |
| :--- | :--- | :--- |
| **Communication** | Automated messages from websites to the server. | Used for server-to-website communication. |
| **Trigger** | Get reports or notifications via HTTP POST only when a new update is made. | Make calls irrespective of data updates. |
| **Data Delivery** | Update applications or services with real-time information. | Need additional implementations to perform real-time updates. |
| **Data Flow Control** | Have less control over data flow. | Have easy control over data flow. |

## 4. OWASP Top 10 API Security Risks

| Risk | Category | Description |
| :--- | :--- | :--- |
| **API1** | Broken Object Level Authorization (BOLA) | APIs expose endpoints handling object IDs; object-level authorization validation is missing; attackers manipulate the ID to access another user's data. |
| **API2** | Broken Authentication | Authentication mechanisms are improperly implemented; attackers compromise authentication tokens or exploit implementation flaws to temporarily or permanently assume other users' identities. |
| **API3** | Broken Object Property Level Authorization | Developers expose all object properties to clients without considering sensitivity; unauthorized access to private/sensitive object properties causes data disclosure, loss, or corruption. Can also lead to privilege escalation or account takeover. |
| **API4** | Unrestricted Resource Consumption | Attackers exploit APIs without limits on client interactions or resource usage; craft requests that control resource parameters; initiate many concurrent requests using automated tools to cause DoS. |
| **API5** | Broken Function Level Authorization | Complex access control policies across hierarchies, groups, and roles cause authorization errors; attackers may gain unauthorized access to administrative functions. |
| **API6** | Unrestricted Access to Sensitive Business Flows | Vulnerable APIs expose critical business flows (e.g., purchasing, posting content) without compensating controls; attackers manually map the workflow and automate access to cause business harm. |
| **API7** | Server-Side Request Forgery (SSRF) | Enables attackers to force the server to send crafted requests to unintended destinations even when protected by firewalls/VPNs; attackers exploit endpoints that accept client-controlled URIs. |
| **API8** | Security Misconfiguration | Attackers search for unpatched flaws, common endpoints, insecure default configs, or unprotected directories; automated tools detect and exploit misconfigurations. |
| **API9** | Improper Inventory Management | Proper management of hosts and API versions is crucial; attackers exploit old API versions or unpatched endpoints; different API versions sharing a database can expose sensitive data. |
| **API10** | Unsafe Consumption of APIs | Developers trust third-party API input more, adopting weaker validation; attackers target integrated third-party services to compromise systems indirectly — leading to data exposure, injections, or DoS. |

## 5. Webhook Security Risks

| Risk | Description | Mitigation |
| :--- | :--- | :--- |
| **Data Exposure in Transit** | Webhooks often transmit data in plain text over HTTP — vulnerable to interception and tampering. | Use **HTTPS** to encrypt all data in transit. |
| **Lack of Verification** | No proper mechanism exists to verify authenticity and integrity of webhook data. | Use **HMAC-based message authentication code** to ensure both sender and receiver are authenticated and the message is untampered. |
| **Replay Attacks** | Attackers intercept legitimate webhook calls and resend them, causing unintended actions. | Add a **timestamp** to the webhook payload and validate it within an acceptable time window. |
| **Unrestricted Sources** | Webhooks allow data from any source by default — enables attackers to send malicious data. | Implement **IP whitelisting** and **mutual TLS** so only trusted sources can send data. |
| **Duplication and Forgery** | Webhook data can be duplicated or forged, leading to data integrity issues. | Use **mutual TLS** to ensure data exchange only between authenticated parties. |
| **Endpoint Configuration Errors** | Misconfigured webhook URLs accidentally send data to the wrong recipient. | Double-check configurations and implement **validation checks** for endpoint URLs. |
| **Forged Requests** | Attackers may forge webhook requests to send malicious data into an application. | Use a **shared secret token** to verify data integrity and accept only authenticated payloads. |
| **Unvalidated Redirects & Forwards** | Webhooks may redirect users to malicious websites if URL redirects aren't validated. | Validate URL redirection against a **whitelist** of approved destinations. |

## 6. API Vulnerabilities

Modern web applications and SaaS platforms use APIs extensively, and poor management of API permissions, flaws in business logic, and exposure of application logic increase the attack surface.

| Vulnerability | Description |
| :--- | :--- |
| **Enumerated Resources** | Design flaws expose sensitive information through unauthenticated public APIs; attackers may guess user IDs easily, compromising user data security. |
| **Sharing Resources via Unsigned URLs** | APIs return URLs to images, audio, video, or other hypermedia resources that are vulnerable to hotlinking. Causes analytics issues, system strain, and enables exploitation. Signed URLs enable rate limiting, auto-expiration, and scoped resource sharing. |
| **Vulnerabilities in Third-Party Libraries** | Developers rely on open-source libraries with constraints/flaws. Not updating libraries or delaying security patches introduces vulnerabilities. |
| **Improper Use of CORS** | Cross-Origin Resource Sharing enables cross-domain communication; improper configuration creates vulnerabilities. Using `Access-Control-Allow-Origin: *` on private APIs can lead to hotlinking and data exposure. |
| **Code Injections** | Unsanitized input enables attackers to inject SQL, XSS, or malicious code into API fields. Attackers may steal sensitive information such as session tokens or user credentials. |
| **RBAC Privilege Escalation** | Role-Based Access Control flaws arise when endpoint permissions aren't updated correctly. Attackers can escalate privileges and access sensitive user information. |
| **No ABAC Validation** | Lack of Attribute-Based Access Control allows attackers to perform unauthorized actions (view, update, delete) on API objects. Missing attribute checks lead to improper authorization. |
| **Business Logic Flaws** | APIs often contain vulnerabilities in business workflows. Attackers exploit legitimate application logic to perform malicious actions. |

**Attacks enabled by API vulnerabilities:**
* DoS attacks
* Code injection attacks
* Unauthorized data access
* Account takeover

## 7. OAuth 2.0 & API Authorization Attacks

**OAuth 2.0** is an authorization framework enabling third-party apps to obtain limited access to user accounts on HTTP services. The **Authorization Code Grant** is the most common OAuth flow.

### Authorization Code Grant Steps:
1. User passes a **GET request** to the client via the user agent (via "Login with" button).
2. Client redirects user agent to the authorization server with:
   * `response_type: code` — informs server which permissions to execute
   * `client_id` — ID assigned to the client
   * `redirect_uri` — where the server redirects after authorization
   * `scope` — defines the level of access
   * `state` — opaque value for security and maintaining request/callback state
3. Upon authentication, user agent is redirected to `redirect_uri` with: `Code` (authorization code) + `State`.
4. Client requests the access token using:
   * `grant_type: authorization_code`
   * `code` — received authorization code
   * `redirect_uri` — used in the first request

### OAuth Attacks:

#### 1. Attack on "Connect" Request
Exploits the "Login with / Connect" button to gain illegal access.

**Steps:**
1. Attacker opens a fake account on the provider's website.
2. Attacker initiates the "Connect" operation but halts authorization server redirects — validates the client to access attacker's resources without informing the client.
3. Attacker spoofs the first request (usually via `<iframe>`) to connect the provider account with the client.
4. When the victim opens the attacker's malicious page, the victim's account is logged out on the provider and connected to the fake account.
5. Attacker can now log into the victim's account using the fake provider account.

#### 2. Attack on `redirect_uri`
Attacker identifies XSS vulnerabilities on the client domain to capture the authorization code.

**Steps:**
1. Attacker leaks data through a vulnerable page: `https://xyz.com/vuln`.
2. Installs malicious JavaScript on the page to send the loaded URL to the attacker.
3. Creates a malicious link that sets `redirect_uri` to the vulnerable page:
   ```
   https://provider.com/oauth/authorize?client_id=CLIENTID&response_type=auth_code&redirect_uri=https%3A%2F%2Fxyz.com%2Fvuln
   ```
4. When victim opens the link, user agent redirects to `https://xyz.com/vuln?code=CODE`.
5. The `CODE` is exfiltrated to the attacker, who uses it with the authentic `redirect_uri`.

#### 3. CSRF on Authorization Response
Performs a CSRF attack to connect a fake account on the provider with the victim's client account.

**Steps:**
1. Attacker opens a fake provider account and initiates a "Connect" operation, halting redirects — stores the `authorization_code`.
2. Attacker persuades the victim to send a request to:
   ```
   https://xyz.com/<provider>/login?code=Auth_Code
   ```
   *(via malicious link embedded with `<img>` or `<script>` tag)*
3. When the victim logs in, the attacker's fake account is connected to the victim's account.
4. Attacker can now sign in as the victim.

#### 4. Access Token Reusage
OAuth requires unique access tokens per client, but access tokens provided for "ClientA" may work for "ClientB".

**Steps:**
1. Attacker develops a legitimate client app "ClientA" enrolled with some provider.
2. Attacker lures the victim into accessing "ClientA" to gain the victim's access token.
3. Attacker opens the URL with ClientB using ClientA's `access_token`:
   ```
   https://clientB.com/callback#access_token=ACCESSTOKEN
   ```
4. "ClientB" verifies the attacker as a valid entity — one access token works on many clients using implicit grant.

#### 5. SSRF Using Dynamic Client Registration Endpoint
OAuth servers have hidden endpoints (e.g., `/connect/register`) that can be exploited for SSRF.

```http
POST /connect/register HTTP/1.1
Content-Type: application/json
Host: server.certifiedhacker.com
Authorization: Bearer eyJhbGciOiJSUzI1NiJ9.eyJ ...

{
  "application_type": "web app",
  "redirect_uris": ["https://client.certifiedhacker.com/callback"],
  "client_name": "Sample Test",
  "logo_uri": "https://client.certifiedhacker.com/logo.png",
  "jwks_uri": "https://client.certifiedhacker.com/public_keys.jwks",
  "sector_identifier_uri": "https://certifiedhacker.com/rdrct_uris.json",
  "request_uris": ["https://client.certifiedhacker.com/rf.txt"]
}
```
*Vulnerable parameters: `logo_uri`, `jwks_uri`, `request_uris` — if the server fetches any of these, SSRF may occur.*

## 8. Web API Hacking Methodology

Attackers use various techniques to identify and exploit vulnerabilities in APIs. Hacking a web API involves the following phases:

### 1. Identify the Target
Before hacking an API, an attacker identifies the target and its perimeter:
* **HTTP:** APIs (SOAP/REST) mostly use HTTP. Request and Response headers are transmitted in plaintext; an attacker can manipulate them to identify the target.
* **Message Formats:** API messages take formats such as JSON (REST) and XML (SOAP). If used incorrectly, they pave the way for vulnerabilities. Attackers can manipulate these formats to identify the target perimeter.

### 2. Detect Security Standards
Although APIs claim security (OAuth, SSL), misconfigurations allow exploitation.
* APIs implement OpenID Connect, SAML, OAuth 1.X/2.X, WS-Security.
* **SSL vulnerabilities:** Often only sensitive data (credit cards) is encrypted, leaving other information in plaintext. Attackers can capture session tokens to retrieve unencrypted account information.

### 3. API Enumeration
Attackers use advanced tools to discover complex API endpoint structures.

**Tool: Kiterunner**
Source: [https://github.com](https://github.com)
Context-aware scanning tool designed for modern web applications relying on APIs.
* **Scan a single target:**
  `kr scan https://target.com:8443/ -w routes.kite -A=apiroutes-210228:20000 -x 10 --ignore-length=34`
* **Scan both http and https:**
  `kr scan target.com -w routes.kite -A=apiroutes-210228:20000 -x 10 --ignore-length=34`
* **Scan a list of targets:**
  `kr scan targets.txt -w routes.kite -A=apiroutes-210228:20000 -x 10 --ignore-length=34`

### 4. Identify the Attack Surface
APIs lack built-in UI fields, so attackers must understand endpoints, messages, parameters, and behavior.
* **API Metadata Vulnerabilities:** Metadata reveals paths, parameters, and formats. REST uses Swagger, RAML, API-Blueprint, I/O Docs; SOAP uses WSDL/XML-Schema. Attackers exploit vulnerabilities in these definitions.
* **API Discovery:** If no metadata exists, attackers configure a local proxy to record mobile app traffic using the target API, then generate metadata.
* **Brute Force:** Attackers brute-force paths (e.g., `/api`, `/api/v2`, `/apis.json`).
* **Analyze Requests/Responses:** Attackers use tools like **Postman** (built-in proxy/interceptor to catch traffic/cookies) and **ReqBin** to intercept and analyze APIs.

### 5. Launch Attacks

#### Fuzzing & Invalid Input Attacks
* **Fuzzing:** Attackers use tools like **Fuzzapi** to repeatedly send random input to generate error messages revealing critical information.
* **Invalid Input:** Sending text instead of numbers, null characters, or exceeding character limits to extract sensitive information from unexpected system behavior. Includes manipulating HTTP headers.

#### Malicious Input Attacks (XML Bomb)
Injecting malicious input directly to target the API and hosting infrastructure using malicious message parsers.
**XML Bomb Example:**
```xml
<?xml version="1.0" encoding="utf-8"?>
<!DOCTYPE lolz [ <!ENTITY lol "lol">
<!ENTITY lol1 "&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;">
<!ENTITY lol2 "&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;">
... (expands up to lol9) ... ]>
<lolz>&lol9;</lolz>
```
When processed by a vulnerable XML parser, this causes a **memory-out-of-bound error (DoS)**. Attackers may also upload malicious script files (e.g., shell script instead of a PDF) to extract filesystem information.

#### Injection Attacks
APIs are vulnerable to SQL, JSON, JavaScript, XPath, and XSLT injections.
* **Normal URL:** `http://billpay.com/api/v1/cust/459`
* **SQL Query executed:** `SELECT * FROM Customers where custID='459'`
* **Injected URL:** `http://billpay.com/api/v1/cust/ '%20or%20'1'='1`
* **Malicious Query:** `SELECT * FROM Customers where custID='' or '1' = '1'` (Returns all customer details).

#### Exploiting Insecure Configurations
* **Insecure SSL:** Self-signed certs allow MITM attacks (sniffing traffic, manipulating client certificates).
* **IDOR:** Modifying direct object references in API calls to access data without authorization.
* **Insecure Session Handling:** Reusing session tokens, unencrypted tokens, or embedding tokens in URLs to hijack client sessions.

#### Login / Credential Stuffing Attacks
Attackers automate previously identified credential pairs to break into accounts using tools like **Sentry MBA** and **PhantomJS**.
* Goal: Disrupt API services, take control of accounts, perform fraudulent transactions.
* Employs bots to bombard the server with login requests.

#### API DDoS Attacks
Saturating an API with massive traffic from a botnet to delay services to legitimate users.
* Bots are created to discover and stay within API rate limit controls to bypass security.
* Attackers may also consume CPU/memory resources reserved for the API to delay service.

*(See Section 7 for details on **OAuth / Authorization Attacks** which are also a core part of this methodology.)*

## 9. Best Practices for API Security

* Use **HTTPS** through SSL/TLS certificates for secure client-server connections.
* Use **server-generated tokens** embedded in HTML as hidden fields for validating incoming requests.
* **Sanitize data** to eliminate malicious scripts; properly validate user input.
* Use an optimized **firewall** to revoke unused, unnecessary files and permissive rules.
* Implement **IP whitelisting** — create a list of trusted IP addresses or IP ranges.
* Use **rate-limiting** to limit the number of API calls per client in a given timeframe.
* **Monitor and maintain access logs** regularly to detect anomalies.
* Implement **pagination** — divide single responses into fragments to prevent oversized payloads.
* Use **parameterized SQL statements** to prevent SQL injection.
* Perform **input validation on the server side** (not client side) to prevent bypassing.
* Conduct **regular security assessments** on all API endpoints using automated tools.
* Use **tokens** to establish trusted identities and control access.
* Use **signatures** to ensure only authorized users can decrypt or modify data.
* Employ **packet sniffers** to detect insecure API calls.
* Use **quotas and throttling** to control and track API usage.
* Implement **API gateways** to authenticate traffic and control/analyze usage.
* Use **advanced bot protection** to prevent sophisticated human-like bots from accessing APIs.
* Implement **MFA** and use protocols like **AppToken, OAuth2, and OpenID Connect**.
* **Document audit logs** before and after every security event; sanitize log data to prevent log injection.
* Use **SOAP APIs** with built-in security features instead of design-based REST APIs where appropriate.
* Confine API response data to requested resource permission status — avoid sharing excessive data.
* Use **WAF security along with TLS/SSL** for securing APIs.
* Ensure all **stateless API requests** (REST) are authorized separately, even from the same user.
* Use **service mesh technology** for multi-service authentication and access control.
* Implement security headers: **`X-Frame-Options`, `X-XSS-Protection`, `Content-Security-Policy`**.
* Regularly perform **SAST, DAST, and penetration testing**.
* Implement proper **error handling** that does not expose sensitive information.
* Implement **token expiration and revocation** mechanisms.

## 10. Best Practices for Securing Webhooks

* Use **HTTPS instead of HTTP** to protect data in transit.
* Use **shared authentication secrets** (e.g., HTTP basic authentication) for all webhooks.
* Implement **webhook signing** to verify data received from email service providers (ESPs); use the **constant time-compare function**.
* Track **`event_id`** to avoid double-processing of the same events (replay protection).
* Ensure the **firewall rejects webhook calls** from unauthorized sources other than the ESP's IP addresses.
* Use **rate limiting** on webhook calls in the web server.
* Compare the **`X-Cld-Timestamp`** of the webhook request with the current timestamp to prevent timing attacks.
* Ensure **event processing is idempotent** — prevent replication of event receipts.
* Ensure the webhook code responds with **`200 OK`** (not 4xx/5xx) in case of errors to prevent webhook deactivation.
* Ensure the webhook URL supports the **HTTP HEAD method** for meta-information retrieval.
* Use **threaded requests** to send multiple requests simultaneously.
* Ensure tokens are stored against **`store_hash`** and not user data.
* Verify clients through **mutual TLS**.
* **Do not send confidential information** via webhooks — use authorized APIs instead.
* Use **HMAC-based signatures** for message verification and payload protection.
* Use a **unique event ID** to record every webhook payload in the database.
* **Log each sent webhook** for debugging.
* Utilize **API keys or similar credentials** to authenticate webhook requests.
* **Limit the size of webhook payloads** to prevent DoS attacks.
* Use a **webhook proxy service** as an extra security layer that can queue, inspect, transform, and retry webhook calls.
* **Verify incoming webhook requests** by checking the source IP against a whitelist or using DNS resolution.
