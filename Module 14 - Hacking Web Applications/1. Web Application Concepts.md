## 1. Introduction to Web Applications

Web applications are software programs that run on web browsers and act as the interface between users and web servers through web pages. They enable users to request, submit, and retrieve data to/from a database over the Internet via a user-friendly GUI. Based on browser-supported languages such as JavaScript, HTML, and CSS, web applications work in combination with SQL to access databases.

### Advantages of Web Applications:
* Independent of the operating system — development and troubleshooting are easy and cost-effective.
* Accessible anytime and anywhere using a computer with an Internet connection.
* The user interface is customizable and easy to update.
* Accessible on any device with an Internet browser (PDAs, smartphones, etc.).
* Dedicated servers monitored by experienced administrators store all application data.
* Multiple server locations increase physical security and reduce monitoring burden.
* Use flexible core technologies: **JSP, Servlets, ASP, SQL Server, .NET, and scripting languages** — scalable and portable.

> **Note:** Although web applications enforce security policies, they are vulnerable to attacks such as SQL injection, cross-site scripting, and session hijacking.

### Popular Web Servers:
`Microsoft IIS`, `Apache HTTP Server`, `H2O`, `LiteSpeed`, `Cherokee`

## 2. How Web Applications Work

The main function of web applications is to fetch user-requested data from a database.

### Request Processing Steps:
1. User enters a website name or URL in the browser.
2. The request is sent to the **web server**.
3. The web server checks the file extension:
   * **HTM/HTML extension** → Web server processes the request directly and sends the file to the browser.
   * **PHP, ASP, CFM extensions** → Web server passes the request to the **web application server**.
4. The web application server processes the request.
5. It accesses the **database** to update or retrieve the requested information.
6. The web application server sends results back to the web server.
7. The web server sends the results to the user's browser.

## 3. Web Application Architecture

Web applications use a set of server-side scripts (Java, C#, Ruby, PHP, etc.) and client-side scripts (HTML, JavaScript, etc.) to execute the application. The architecture consists of **three layers**:

### Layer 1: Client / Presentation Layer
All physical devices on the client side (laptops, smartphones, computers). Features OSes and compatible browsers that allow users to send requests. The user enters a URL → request travels to the web server → server fetches data → browser displays the response.

### Layer 2: Business Logic Layer
Consists of two sub-layers:

#### Web-Server Logic Layer
Contains: Firewall, HTTP request parser, proxy caching server, authentication/login handler, resource handler, hardware server.
* **Firewall:** Secures the content.
* **HTTP request parser:** Handles client requests and forwards responses.
* **Resource handler:** Handles multiple requests simultaneously.
* Examples: **IIS Web Server, Apache Web Server**.

#### Business Logic Layer
Implements functional logic using **.NET, Java, and "middleware"**. Defines the flow of data, stores application data, integrates legacy apps. Contains the software and defines the steps to search and fetch data.

### Layer 3: Database Layer
Consists of cloud services, a **B2B layer** for commercial transactions, and a **database server** supplying production data in structured form.
* Examples: **MS SQL Server, MySQL Server**.

## 4. Web Services

A web service is an application or software deployed over the Internet. It uses a standard messaging protocol (such as **SOAP**) to enable communication between applications on different platforms (e.g., Java-based services interacting with PHP applications).

Web-based applications are integrated with **SOAP, UDDI, WSDL, and REST** across the network.

---

## 5. Web Service Architecture

Describes the interactions among the **service provider, service requester, and service registry** via three operations: **Publish, Find, and Bind**.

### Three Roles:
1. **Service Provider:** The platform that provides services. Deploys and publishes service descriptions to the service registry.
2. **Service Requester:** An application or client seeking a service (e.g., a browser acting on behalf of the user). Finds descriptions from the registry and invokes the service.
3. **Service Registry:** The place where providers load service descriptions. Requesters discover the service and retrieve binding data.

### Three Operations:
1. **Publish:** Service descriptions are published to allow requester discovery.
2. **Find:** The requester obtains service descriptions — at development time (interface description) and at run time (binding and location).
3. **Bind:** The requester calls and establishes communication with services at run time using binding data inside service descriptions.

### Two Artifacts:
1. **Service:** A software module offered by the service provider over the Internet. Communicates with requesters; can also serve as a requester.
2. **Service Description:** Provides interface and implementation details — all operations, network locations, binding details, datatypes. Can be stored in a registry.

### Components of Web Service Architecture:
| Component | Description |
| :--- | :--- |
| **UDDI** | Universal Description, Discovery, and Integration — a directory service listing all available services. |
| **WSDL** | Web Services Description Language — an XML-based language that describes and traces web services. |
| **WS-Security** | Web Services Security — an extension of SOAP maintaining integrity and confidentiality of SOAP messages and authenticating users. |
| **WS-Work Processes** | Defines the process flow of web services. |
| **WS-Policy** | Specifies the capabilities and requirements of web service entities. |
| **WS-Security Policy** | Specifies security policies for web services. |

## 6. Characteristics of Web Services

| Characteristic | Description |
| :--- | :--- |
| **XML-based** | Use XML for data representation and transportation — avoids OS/network/platform binding. |
| **Coarse-grained service** | Objects containing large amounts of information; a combination of multiple fine-grained services. |
| **Loosely coupled** | Supports loose coupling via the web API using XML messages — flexible and adaptable. |
| **Asynchronous & Synchronous** | Sync: users wait for a response (RPC-based). Async: users do not wait (document-based). Both implemented via Servlets, SOAP/XML, and HTTP. |
| **RPC support** | Supports remote procedure calls similarly to traditional applications. |

---

## 7. Types of Web Services

### 1. SOAP Web Services
Uses the **Simple Object Access Protocol (SOAP)** which defines the XML format. XML is used to transfer data between the service provider and requester. Determines the procedure to build web services and enables data exchange between different programming languages.

### 2. RESTful Web Services
**REpresentational State Transfer (RESTful)** — designed for greater productivity. Uses many underlying HTTP concepts. An **architectural approach** rather than a protocol (unlike SOAP).

## 8. Vulnerability Stack

Web applications are accessible through multiple layers, each with its own elements, mechanisms, and services. The **Vulnerability Stack** shows how all seven layers make web applications vulnerable. Attackers exploit vulnerabilities in one or more layers to gain unrestricted access.

| Layer | Element | Vulnerability |
| :--- | :--- | :--- |
| **Layer 7 (Custom Web App)** | Business logic (.NET, Java) | Input validation attacks such as **XSS**, exploiting vulnerabilities in the business logic. |
| **Layer 6 (Third-Party Components)** | Payment gateways (e.g., Citrix.com via Amazon.com) | Attackers exploit redirection through third-party services to enter the main website. |
| **Layer 5 (Web Server)** | Apache, IIS, Nginx | Footprinting/banner grabbing reveals server name and version; attackers search **CVE database** for exploits. |
| **Layer 4 (Database)** | User IDs, passwords, personal data | Attackers use tools like **SQLmap** to exploit database vulnerabilities. |
| **Layer 3 (Operating System)** | Open ports, services | Attackers scan for open ports, develop viruses/backdoors, send malware through open ports. |
| **Layer 2 (Network)** | Routers, switches, CAM tables | Attackers flood switches (CAM table exhaustion), causing hub-like behavior to sniff credentials. |
| **Layer 1 (Security)** | IDS, IPS | Attackers adopt evasion techniques to circumvent IDS/IPS and avoid triggering alarms. |
