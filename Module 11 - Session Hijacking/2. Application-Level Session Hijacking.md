## 1. Core Methods to Obtain Session IDs

An attacker gains control over a valid user's active session by obtaining their session ID using three primary categories of techniques:

1. **Stealing:** Acquiring the session key through physical access (local memory/files) or by using network sniffing tools (Wireshark, Riverbed Packet Analyzer Plus) to extract IDs from HTTP packets.
2. **Guessing:** Observing session variables and attempting to guess the ID. This is only effective when the server uses weak or flawed session-ID generation mechanisms, making the range of possible IDs small.
3. **Brute Forcing:** Attempting all possible permutations of session ID values until finding one that works. An attacker on a DSL line can generate up to 1,000 session IDs per second. This is highly effective against non-random algorithms. *(Note: If the predicted range of values is very small, a brute-force attack is often referred to as a **session prediction attack**).*

## 2. Compromising IDs via Sniffing & Prediction

### A. Session Sniffing
A web server sends a session token (usually a variable-width string) to the client browser after successful login. The token resides in the HTTP header (cookie), the URL, or the HTTP body.
* The attacker uses packet sniffing tools to intercept the HTTP traffic.
* Once the session ID is extracted, the attacker masquerades as the victim and sends the ID to the web server before the victim does, seizing control of the session.

### B. Predicting Session Tokens
If an attacker can guess or predict the ID based on weak generation algorithms, they bypass authentication entirely. Attackers gather a large sample of simultaneous session IDs to analyze the variable sections and determine the underlying pattern.

**How Tokens are Predicted:**
* **Sequential Tokens:** Issued in order (e.g., 1001, 1002, 1003). By intercepting 1002, the attacker predicts the next user will receive 1003.
* **Timestamp-based Tokens:** Tokens incorporating predictable elements like the current date and time (e.g., `user123-20240611T1234`).
* **Small Token Space Size:** If tokens only range from 0000 to 9999, the attacker writes a script to try all 10,000 possible values.
* **Lack of Rate-Limiting:** Without blocking failed attempts, an attacker can attempt thousands of tokens per minute indefinitely.
* **Weak Pseudorandom Number Generators (PRNGs):** Poorly seeded PRNGs (like using the current time as a seed) allow attackers to replicate the token generation algorithm perfectly.

## 3. Man-in-the-Middle & Man-in-the-Browser Attacks

### Man-in-the-Middle (MITM)
The attacker intrudes into an existing connection, splitting a TCP connection into two: Client-to-Attacker and Attacker-to-Server. 
* The attacker can read, modify, and insert fraudulent data into the HTTP transaction.

### Man-in-the-Browser (MITB)
Similar to MITM, but executed via a **Trojan horse** installed directly inside the victim's browser.
* The Trojan intercepts and manipulates calls between the browser and its security mechanisms.
* **Highly Dangerous:** MITB succeeds even if the connection uses SSL/TLS, PKI, or Two-Factor Authentication, because the malware operates *inside* the trusted browser environment before encryption occurs.
* **Execution Steps:**
  1. Trojan infects the OS/Application.
  2. Installs malicious extension files in the browser config.
  3. Registers a handler for targeted URLs (like banking sites).
  4. When the victim logs in and clicks a button, the extension uses the Document Object Model (DOM) to extract and modify form values.
  5. The server processes the modified (fraudulent) transaction.
  6. The browser receives the receipt, but the Trojan alters the display so the victim sees the original, unmodified details.

## 4. Client-Side Attacks (XSS & CSRF)

Client-side attacks target vulnerabilities in the client application (usually the browser).

### Cross-Site Scripting (XSS)
Attackers inject malicious client-side scripts (JavaScript, VBScript, ActiveX, Flash) into web pages viewed by other users.
* A dynamic page executes the malicious script on the victim's machine.
* **Example Payload:** `<SCRIPT>alert(document.cookie);</SCRIPT>`
* The script silently steals the victim's cookies and sends them to the attacker, who uses them to establish a valid session.

### Cross-Site Request Forgery (CSRF)
Also known as a **one-click attack** or **session riding**. The attacker exploits the victim's active session with a trusted site to perform malicious activities (e.g., transferring funds, changing account info).
* **Difference from XSS:** XSS exploits the trust a user has for a website; **CSRF exploits the trust a website has for a user's browser.**
* **Execution Steps:**
  1. Attacker hosts a webpage containing a malicious, hidden request form.
  2. Victim (already logged into their bank) is lured to the malicious page.
  3. The page automatically submits the form to the bank.
  4. Because the victim has an active session cookie, the bank accepts the request as legitimate.

## 5. Session Replay & Session Fixation

### Session Replay Attack
The attacker captures an authentication token by eavesdropping on the network. They then "replay" the exact same authentication request to the server using the captured token to dodge authentication and gain access.

### Session Fixation Attack
Instead of stealing a session *after* the user logs in, the attacker fixes a known session *before* the user logs in.
* **The Vulnerability:** The web application accepts existing session IDs instead of generating a new, secure one upon login.
* **Execution Phases:**
  1. **Set-up Phase:** Attacker establishes a connection with the web server and receives a legitimate session ID (the "trap" ID). They may need to ping the server to keep it alive.
  2. **Fixation Phase:** Attacker sends a link to the victim containing the trap ID (e.g., `http://citibank.com/?SID=0D6441FEA`).
  3. **Entrance Phase:** The victim clicks the link and logs into the bank. The bank links the victim's credentials to the trap ID. The attacker, who already has the trap ID, now has full access to the victim's authenticated session.

## 6. Advanced Attacks (Proxy, CRIME, Forbidden, Donation)

| Attack Type | Description |
| :--- | :--- |
| **Proxy Servers** | Attacker lures victim to a fake link that routes through the attacker's proxy. The proxy forwards the request to the real server, capturing all session data in transit. |
| **CRIME Attack** | *(Compression Ratio Info-Leak Made Easy)*. A client-side attack exploiting data-compression features in SSL/TLS, SPDY, and HTTPS (specifically the DEFLATE algorithm). By observing the compressed size of HTTPS requests injected with malicious data, the attacker deduces the authentication cookie character by character. |
| **Forbidden Attack** | A MITM attack executed when a cryptographic **nonce is reused** during an HTTPS session using AES-GCM encryption. Reusing the nonce allows the attacker to hijack the TLS handshake, monitor the connection, and inject malicious JavaScript prompting the user for sensitive data. |
| **Session Donation** | The attacker logs into a service to get a valid Session ID, then "donates" this ID to the victim. When the victim enters sensitive info (like payment details), that info is saved into the *attacker's* account instead of the victim's. |

## 7. Session Hijacking Tools

Security professionals and attackers use sophisticated interception proxies to perform application-level session hijacking:

* **Hetty:** (https://github.com/hettysoftware/hetty) An HTTP toolkit for security research featuring a MITM HTTP proxy, logs, and manual request editing/replaying.
* **Caido:** (https://caido.io) A web security auditing toolkit to intercept and view HTTP requests in real-time, modifying them automatically with Regex rules.
* **bettercap:** (https://www.bettercap.org) A portable framework in Go for reconnaissance and MITM attacks on Wi-Fi, Bluetooth LE, and IPv4/IPv6 networks.
* **Burp Suite:** (https://portswigger.net) The industry standard interception proxy.
* **OWASP ZAP:** (https://www.zaproxy.org) Open-source alternative to Burp Suite.
* **WebSploit Framework:** (https://sourceforge.net/projects/websploit/)
* **sslstrip:** (https://moxie.org/software/sslstrip/) Strips HTTPS down to HTTP to capture credentials in plaintext.
* **JHijack:** (https://sourceforge.net/projects/jhijack/)
