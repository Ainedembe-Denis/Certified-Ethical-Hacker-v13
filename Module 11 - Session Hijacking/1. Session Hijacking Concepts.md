## 1. What is Session Hijacking?

After successful user authentication, a web server sends a **session identification token (or key)** to the web client. This token differentiates multiple sessions that the server establishes with various clients. 

**Session Hijacking** is an attack in which an attacker takes over a valid Transmission Control Protocol (TCP) communication session between two computers. Because most authentication happens only at the *start* of a TCP session, an attacker can gain access to a machine while the session is already in progress.

**Key Concepts:**
* **Exploitation:** The attack exploits the session-token generation mechanism or token security controls.
* **Goal:** To guess or steal a valid session ID to establish an unauthorized connection with the target server. The server responds to the attacker's requests under the illusion that it is communicating with the authenticated user.
* **Attack Vectors:** Can be used to launch **Man-in-the-Middle (MITM)** attacks (placing the attacker between an authorized client and server) or **Denial-of-Service (DoS)** attacks by sniffing sensitive information and disrupting sessions.

> **💡 CEH Beginner Tip:** Think of authentication like showing your ticket at the entrance to a concert, and the session token is a wristband you are given. Session hijacking is when an attacker steals your wristband once you are already inside, allowing them to freely roam the VIP areas without ever needing a ticket.

## 2. Why is Session Hijacking Successful?

Session hijacking succeeds primarily due to vulnerabilities in how sessions and TCP/IP are designed and handled. The key factors include:

| Vulnerability Factor | Description |
| :--- | :--- |
| **Absence of Account Lockout** | If a site doesn't lock out invalid session IDs, an attacker can launch a **brute-force attack** with varying session IDs embedded in genuine URLs until a valid one is found. |
| **Weak Session ID Generation** | Using predictable, linear algorithms (based on time or IP address) or using **small/short session IDs** makes it easy for attackers to narrow the search space and forge a valid ID. |
| **Insecure Handling of IDs** | Attackers can mislead a browser into visiting malicious sites to retrieve stored session IDs (via XSS, browser bugs, or DNS poisoning). |
| **Indefinite Session Timeout** | Session IDs with infinite expiration (e.g., "Remember Me" options) give attackers unlimited time to guess or steal static IDs, sometimes by breaking into proxy servers that log them. |
| **TCP/IP Design Flaws** | Most machines running TCP/IP are vulnerable due to inherent design flaws in the protocol itself. |
| **Lack of Encryption** | Countermeasures fail without proper encryption. Session IDs are easily sniffed in flat networks if transport security (like SSL/TLS) is not configured properly. |

## 3. The Session Hijacking Process

Hijacking a session allows an attacker to stay connected for hours without arousing suspicion, planting backdoors or gaining further access. The process is divided into three broad phases:

### Phase 1: Tracking the Connection
* The attacker uses a network sniffer or a tool like **Nmap** to scan for a target with a TCP sequence that is easy to predict.
* The attacker identifies the victim and captures the **Sequence (SEQ)** and **Acknowledgment (ACK)** numbers.
* TCP relies on these numbers to track the communication order.

### Phase 2: Desynchronizing the Connection
* **Desynchronization** occurs when a connection is stable, but the server's sequence number does not match the client's acknowledgment number (or vice versa).
* **How it's done:**
  1. The attacker sends **null data** to the server. The server's SEQ/ACK numbers advance, but the victim's machine doesn't register the increment.
  2. Alternatively, the attacker sends a **Reset (RST)** flag to break the connection on the server side in the early setup stage. 
  3. The attacker immediately sends a new SYN packet with identical parameters but a *different* sequence number.
  4. The server creates a new connection and sends a SYN/ACK.
  5. The attacker responds with an ACK, successfully establishing a desynchronized state where the attacker controls the session.
* **The "ACK Storm" Flaw:** If a FIN flag is used improperly or an unacceptable packet is sent, the host acknowledges it by sending the expected sequence number. This mismatch can create an endless loop of ACK packets generating excess network traffic (an ACK storm).

### Phase 3: Injecting the Attacker's Packet
* With the connection interrupted/desynchronized, the attacker can:
  * Inject data into the network by spoofing an IP address.
  * Actively participate as a **Man-in-the-Middle (MITM)**, reading, modifying, and passing data between the target and server at will.

## 4. Types of Session Hijacking

Session hijacking is categorized based on the attacker's level of involvement:

### Passive Session Hijacking
* The attacker **monitors and records** an ongoing session without taking it over.
* Uses network sniffers to obtain user IDs, passwords, and raw access to a network.
* **Countermeasures:** Identification schemes (One-time passwords like S/KEY) or ticketing (Kerberos) protect data from sniffing, but data must be encrypted or digitally signed.

### Active Session Hijacking
* The attacker actively **takes over an existing session** by breaking the connection on one side or participating directly (e.g., MITM attack).
* Requires predicting sequence numbers before the target responds.
* **Note:** On modern networks, OS vendors use random values for initial sequence numbers, making active prediction significantly harder.

## 5. Session Hijacking in the OSI Model

Hijacking attacks target different layers of the OSI model:

### Network-Level Hijacking (Transport / Network Layers)
* Interception of packets between a client and server in a TCP or UDP session.
* Attackers prefer this because it does not require host access or modifying the attack on a per-web-application basis. It attacks the data flow protocol shared across all applications.
* Provides crucial information used to launch application-level attacks.

### Application-Level Hijacking (Application Layer)
* Gaining control over an HTTP user session by obtaining session IDs.
* Attackers steal the ID to gain control of an existing session and create new unauthorized sessions.
* Usually occurs in conjunction with network-level hijacking.

## 6. Spoofing vs. Hijacking

While related, spoofing and hijacking are distinct attack methodologies:

| Feature | IP Spoofing | Session Hijacking |
| :--- | :--- | :--- |
| **Objective** | Pretend to be another user/machine to gain initial access. | Take over an *already existing* active session. |
| **Session Status** | Initiates a **new** session using stolen credentials. | Displaces a legitimate user to hijack an **active** session. |
| **Sequence Numbers** | Guesses/predicts the Next Sequence Number (NSN). | Requires knowledge of the Initial Sequence Number (ISN) and packet exchange numbers. |
| **Attacker Visibility** | In "blind spoofing", the attacker cannot view the responses from the server. | Attacker observes and interacts with responses (often using source routing). |
| **Difficulty** | Easier to perform (simple IP spoofing). | Highly difficult; requires precise control and specific tools. |

### Advanced Spoofing/Hijacking Concepts:
* **Blind Hijacking:** Predicting sequence numbers without observing the replies. Useful when exploiting trust relationships between remote machines, but the attacker cannot view the response.
* **Source Routing:** A process allowing the sender to specify the route an IP packet takes. In session spoofing, attackers use source routing to ensure returning traffic passes by their sniffer, allowing them to capture credentials and establish a session.

> **💡 CEH Beginner Tip:** **Spoofing** is forging a fake ID to walk through the front door. **Hijacking** is waiting for someone with a real ID to open the door, knocking them out of the way, and taking their place before the door closes. Both are defeated by encryption (SSL/TLS) and per-packet integrity checking, which prevents attackers from participating in the key exchange.
